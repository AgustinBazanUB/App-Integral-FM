# V1.1 · Ventas, Ubicaciones y Panel Vendedor · estado final

## Alcance

Esta etapa modifica la aplicación integral existente. No crea una segunda aplicación ni una segunda colección de ventas.

Fuente funcional histórica inspeccionada: `AgustinBazanUB/FM-stock-y-ventas`, especialmente `seller.js`, `discounts.js`, `payments.js`, `firebase-service.js`, `keyboard.js`, `offline-sales.js`, `locations.js`, `categories.js`, `utils.js` y `app.js`.

La apariencia antigua no se copia. La lógica válida se conserva dentro de React/Vite y del design system actual.

## Fuente de verdad

El flujo operativo continúa siendo:

`Administrador → Ubicación → productos / stock / vendedores / descuentos`

`Vendedor → ubicación autorizada → productos / stock / descuentos → venta`

`Venta → sales → locationId → Ubicación / Ventas / Métricas`

Existe un único documento de venta en `sales`. La pantalla Ventas de una ubicación consulta esa colección por `locationId`; no copia documentos a una subcolección.

## Carga de stock

`LocationDetailPage` ya utiliza un `input` compacto para Motivo y lo coloca junto a Modo de carga en escritorio. En mobile ambos controles se apilan.

La operación real reutiliza `loadActiveLocationStock` y `loadLocationStock`:

- vuelve a leer la ubicación;
- valida que siga activa;
- limita la operación;
- valida productos;
- calcula stock sin permitir negativos;
- guarda `locationStock`;
- crea `stockMovements`;
- crea `stockOperations` con idempotencia;
- crea auditoría.

## Panel Vendedor

Se conserva la arquitectura React existente:

- `SellerPanel`
- `DiscountDialog`
- `MultiplePaymentDialog`
- hooks de vendedor
- `sellerService`
- IndexedDB de pendientes
- dominios compartidos de descuentos y pagos.

La Venta actual permanece compacta, con catálogo, carrito, descuentos resumidos, pagos, ticket y acción final.

Los controles de eliminar del carrito y de descuentos aplicados se elevan a 44 × 44 px y en 480/390/320 px el carrito reorganiza filas para evitar scroll horizontal.

## Descuentos

La función única es `calculateDiscountSummary`.

Orden obligatorio:

1. subtotal bruto;
2. todos los descuentos fijos;
3. base porcentual resultante;
4. porcentajes sucesivos sobre el saldo;
5. total mínimo cero.

Ejemplo de regresión:

`100.000 - 10.000 - 10 % = 81.000`.

Los descuentos guardados se vuelven a validar en el servicio contra Firestore antes de confirmar la venta. Se comprueban actividad, vigencia, ubicación, rol, producto/categoría cuando corresponda y asignación a la ubicación.

Los manuales sólo se aceptan con permiso, valor entero mayor a cero y porcentaje máximo 100.

## Pagos

El dominio compartido conserva:

- Efectivo;
- Débito;
- Crédito;
- Alias;
- +2 pagos.

`+2 pagos` exige al menos dos medios con monto positivo, impide importes inválidos o negativos, muestra total cargado/diferencia y sólo normaliza cuando la suma coincide exactamente con la venta.

## Botonera

Se mantiene la coincidencia histórica por `key`, `code` y `location`.

La captura no intercepta `input`, `textarea`, `select`, contenido editable ni modales.

Se conservan producto, descuento, Enter/Continuar, suma/resta y atajos de formas de pago.

Se restauró `generateTicket` como acción de botonera. En React solamente alterna la solicitud `ticketRequested`; nunca emite un comprobante fiscal.

## Ticket / futura ARCA

Estado actual:

- no solicitado: `ticketRequested=false`, `ticketStatus="not_requested"`;
- solicitado: `ticketRequested=true`, `ticketStatus="pending"`.

No se generan CAE, número fiscal ni comprobantes ficticios.

Una integración futura deberá ejecutarse desde backend seguro. Credenciales fiscales no pertenecen al bundle React, al repositorio ni a documentos públicos de Firestore.

## Registro de venta y stock

`createSellerSale` vuelve a validar:

- permiso;
- ubicación autorizada y activa;
- descuentos;
- pagos;
- ticket;
- registros reales de stock.

Dentro de una única transacción Firestore:

- resuelve contador y código;
- vuelve a leer cada stock;
- aborta si la cantidad disponible cambió;
- impide stock negativo;
- actualiza stock;
- registra cada movimiento;
- crea un único documento en `sales`;
- crea auditoría.

Una falla aborta toda la operación.

## Modelo de venta

El ID del documento Firestore es el identificador canónico de venta y no se duplica innecesariamente en otro campo `saleId`.

Campos actuales relevantes:

- `saleCode`;
- `locationId`, `locationName`, `locationPrefix`;
- `sellerId`, `sellerName`;
- `createdBy`, `createdByName`;
- `createdAt`, `updatedAt`, `saleDate`, `saleTime`;
- `items[]`: `productId`, nombre, abreviación, cantidad, precio unitario y subtotal;
- `discounts[]`: id, nombre, fuente, tipo, valor e importe aplicado;
- `fixedDiscountTotal`, `percentageDiscountTotal`, `discountTotal`;
- `subtotal`, `totalBeforeDiscounts`, `totalItems`, `total`;
- `paymentMethod`, `paymentMethodLabel`, `payments[]` cuando corresponde;
- `status`;
- `ticketRequested`, `ticketStatus`;
- campos offline cuando la venta proviene de una sincronización.

## Offline

Las ventas sin conexión permanecen en IndexedDB como pendientes y no se presentan como confirmadas.

Conservan `localId` idempotente. Al sincronizar, `createSellerSale` usa un documento determinista para ese `localId`; si ya existe devuelve la misma venta. Antes de sincronizar vuelve a validar ubicación, descuentos y stock real. Un conflicto queda como `sync_error` y no modifica stock silenciosamente.

## Ventas por ubicación

`LocationDetailPage` mantiene el orden:

1. Productos
2. Cargar stock
3. Vendedores
4. Descuentos
5. Ventas

`LocationSalesPanel` consulta `sales` por `locationId`, ordena `createdAt` descendente y pagina con cursor.

El registro muestra código, fecha/hora, vendedor, cantidad, total, pago, estado y ticket cuando corresponde. Incluye filtros básicos de fecha, vendedor, estado y forma de pago.

El detalle muestra:

- estado, fecha/hora, ubicación y vendedor;
- líneas de producto con imagen, nombre, abreviación, cantidad, precio y subtotal;
- descuentos con fuente/tipo/valor/importe;
- partes de pago;
- subtotal, descuentos fijos, porcentuales, total descuentos y total final;
- ticket;
- creador, edición y anulación cuando existen.

La anulación administrativa reutiliza `cancelSellerSale`, devuelve stock de forma transaccional y conserva historial. El motivo es opcional, igual que en Panel Vendedor.

## Navegación y mobile

Las cinco secciones de Ubicaciones tienen contraste permanente:

- base `#F7F1E8` / `#2F2924` / `#DED6CC`;
- seleccionada `#F3E8CF` / `#76510F` / `#B88A2D`.

No se depende del hover para leer el estado.

Se mantienen foco visible, targets táctiles, bottom sheet de descuentos, acción Continuar sticky, `prefers-reduced-motion` y layouts específicos hasta 320 px cuando es posible.

## Firestore

No se agrega una colección paralela.

Consulta principal de historial:

`where("locationId", "==", locationId) + orderBy("createdAt", "desc") + startAfter(cursor) + limit(pageSize)`.

El índice `sales: locationId ASC + createdAt DESC` ya existe. También existen índices para vendedor y estado, por lo que esta etapa no necesita nuevos índices.

Las reglas actuales ya restringen ventas, stock, movimientos y auditoría por rol/permiso y ubicación. No se realiza una migración destructiva ni se modifican reglas sólo por duplicar validaciones que ya existen.
