# Versión 1.1 · Correcciones de anulación, foco y Métricas Generales

## Alcance

Esta corrección trabaja sobre la aplicación integral existente de Flor Mía. No reconstruye módulos ni modifica la arquitectura base de React, Vite, Firebase Authentication, Cloud Firestore, permisos, stock, ventas pendientes offline, GitHub o Netlify.

Se corrigen cuatro problemas relacionados:

1. pérdida de foco al escribir el motivo de anulación en Panel Vendedor;
2. pérdida de foco equivalente en formularios contenidos dentro de `Modal` y `Drawer`;
3. navegación diferente entre accesos a Métricas Generales;
4. filtros de Historial y análisis de ventas recortados por paneles o stacking contexts.

## Diagnóstico y solución

### Pérdida de foco en Motivo

`SellerPanel` mantiene `cancelReason` en estado React, pero originalmente el ciclo de foco del overlay dependía de la identidad de `onClose`. Un callback inline nuevo en cada render hacía que el efecto se limpiara y se armara otra vez al escribir cada carácter.

La corrección definitiva vive en el design system:

- `onClose` se conserva en `onCloseRef`;
- el efecto de `useOverlay` ya no depende de la identidad de `onClose`;
- Escape usa siempre el callback actual;
- Tab / Shift+Tab mantienen el focus trap;
- al cerrar se restaura el foco al elemento disparador;
- no existe `focus()` por tecla;
- no existen escrituras Firestore en `onChange`.

`SellerPanel` conserva además un `closeCancelDialog` estable para el diálogo de anulación.

### Motivo opcional

El servicio normaliza:

```js
const safeReason = String(reason || "").trim() || null;
```

Si existe texto se guarda el campo existente `cancelReason`. Si está vacío, no se agrega el campo a la actualización.

En ambos casos se mantienen:

- `status: "cancelled"`;
- `cancelledAt`;
- `cancelledBy`;
- `cancelledByName`;
- devolución transaccional de stock;
- movimiento `sale_cancel`;
- auditoría `sale.cancelled`;
- compatibilidad temporal con reglas Firestore anteriores.

La interfaz muestra `Motivo de anulación (opcional)` y el botón de anulación no depende de la longitud del texto.

## Métricas Generales

### Ruta canónica

La única ruta canónica es:

`/gestion/metrics/sales`

Se centraliza en:

```js
SALES_METRICS_PATH = "/gestion/metrics/sales";
```

- `getManagementPath("metrics")` devuelve esa constante;
- Dashboard usa la misma constante para `Ver todas las métricas`;
- sidebar desktop y menú hamburguesa comparten `renderNavigation()` y `getManagementPath()`;
- `ManagementApp` renderiza `SalesMetricsPage` para el módulo `metrics`;
- cualquier deep link anterior dentro de `/gestion/metrics...` se redirige a la ruta canónica.

No se crea una segunda pantalla, un segundo hook ni una segunda consulta de métricas.

## Filtros de Métricas

### Causa del clipping

El design system usa `overflow: hidden` en `.fm-panel`. Un dropdown posicionado dentro de ese árbol puede ser recortado aunque su `z-index` sea mayor, porque sigue atrapado por el overflow y los stacking contexts de sus ancestros.

### Solución estructural

El layer abierto de cada filtro se renderiza con:

```js
createPortal(..., document.body)
```

El trigger permanece dentro del panel, pero el contenido abierto queda fuera del árbol que puede recortarlo.

En desktop/tablet:

- se obtiene `getBoundingClientRect()` del trigger;
- el portal se posiciona con `position: fixed`;
- se limita el ancho y la altura al viewport;
- se abre debajo del botón cuando hay espacio;
- si falta espacio inferior, puede abrirse por encima;
- se recalcula en `resize` y `scroll` mientras está abierto.

En mobile:

- el mismo portal adopta presentación bottom sheet;
- respeta `safe-area-inset-bottom`;
- mantiene scroll interno;
- encabezado y acciones permanecen accesibles;
- se contemplan 768, 480, 390 y 320 px.

No se agregó ninguna dependencia externa.

### Jerarquía visual

Se agregó el token de design system:

```css
--fm-z-popover: 80;
```

Esto mantiene el popover por encima de contenido, header y resultados comunes, pero por debajo del menú móvil y de los modales principales del design system (`z-index: 1000`).

### Interacción

Los multiselect usan borrador local hasta confirmar:

- Ubicaciones;
- Vendedores;
- Productos/categorías;
- Descuentos;
- Forma de pago.

Reglas:

- sólo un filtro puede estar abierto;
- `Aplicar` confirma;
- `Cancelar` restaura el estado previo;
- click/tap exterior cierra;
- Escape cierra;
- Tab / Shift+Tab permanecen dentro del diálogo abierto;
- al cerrar se restaura foco al trigger;
- listeners de `pointerdown`, `keydown`, `resize` y `scroll` existen sólo durante la apertura y se limpian al cerrar;
- listas largas usan scroll interno y no exceden el viewport.

El filtro de forma de pago reutiliza `SINGLE_PAYMENT_METHODS` del dominio central de pagos para no duplicar identificadores.

## Integridad y rendimiento

- no se guarda Motivo mientras se escribe;
- no se consulta Firestore por cada tecla;
- no se modifica la fórmula de stock al anular;
- no se borra físicamente la venta;
- no se duplica la consulta de Métricas;
- no se crea otra instancia de `SalesMetricsPage`;
- sólo existe un portal de filtro mientras un filtro está abierto;
- los listeners globales del filtro se desmontan al cerrar;
- no se modifica la cola IndexedDB de ventas pendientes offline.
