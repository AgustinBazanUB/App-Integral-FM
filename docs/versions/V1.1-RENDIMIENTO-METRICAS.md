# Versión 1.1 · Envío 6 · Rendimiento, métricas y conectividad

## Alcance

Este envío optimiza la aplicación integral existente de Flor Mía. No reconstruye la plataforma y mantiene React, Vite, Firebase Authentication, Cloud Firestore, roles, permisos, Netlify, Panel Administrador, Panel Vendedor, botonera Bluetooth y ventas pendientes offline.

La especificación original incluía convertir offline a solo lectura. Durante la implementación se recibió una corrección explícita: **no aplicar modo solo lectura y no desactivar ventas pendientes offline**. Por lo tanto la cola local, la sincronización y la idempotencia del Panel Vendedor permanecen activas.

## Auditoría inicial

### Cuellos de botella encontrados

1. `ManagementApp.jsx` importaba estáticamente casi todas las páginas de gestión y el Panel Vendedor. Entrar al Panel General obligaba a procesar código de módulos que no estaban abiertos.
2. `App.jsx` importaba al mismo tiempo la tienda pública y la gestión privada, aunque el usuario estuviera usando solamente una de ellas.
3. Dashboard, Métricas y Vendedor podían volver a consultar ubicaciones aunque el resultado siguiera vigente.
4. El estado online/offline se escuchaba desde más de un hook, creando detectores independientes.
5. La botonera recorría linealmente productos, descuentos y acciones ante cada pulsación.
6. El módulo Métricas existente permitía pocos filtros y realizaba un análisis más limitado que la estructura de ventas ya disponible.
7. El menú mobile podía beneficiarse de scroll táctil nativo explícito, menos efectos visuales costosos y animaciones basadas sólo en transform/opacity.
8. El cambio Administrador → Vendedor no aprovechaba una precarga ociosa del bundle crítico ni la lista de ubicaciones ya leída en administración.

### Arquitectura conservada

- React 18.3.1.
- Vite 6.x.
- Firebase 12.x.
- Router SPA propio.
- `AuthProvider` y sesión Firebase persistente.
- Firestore como fuente real de datos.
- Servicios y dominio modular existentes.
- Netlify + GitHub.

## Rendimiento crítico

### Separación Tienda / Gestión

Se creó `src/Storefront.jsx` y `App.jsx` ahora carga con `React.lazy`:

- `ManagementApp` para rutas privadas.
- `Storefront` para la tienda.

La gestión ya no descarga por adelantado páginas públicas que no utiliza y viceversa.

### Lazy loading por módulo de gestión

Dashboard, Login y control de acceso permanecen disponibles inmediatamente.

Se cargan bajo demanda:

- Panel Vendedor.
- Ubicaciones.
- Detalle de ubicación.
- Venta Rápida.
- Métricas.
- Administración.
- Actividad.
- Auditoría.
- Ajustes.
- Módulos genéricos.

La transición usa skeletons con el fondo de la aplicación, evitando una pantalla negra entre módulos.

### Precarga selectiva del Panel Vendedor

Cuando un administrador autenticado tiene permiso de vendedor:

1. primero se renderiza Administración;
2. cuando el navegador queda ocioso se precarga el chunk `SellerPanel`;
3. se precarga la lista autorizada de ubicaciones mediante la misma caché usada por Dashboard;
4. no se precarga stock de todas las ubicaciones;
5. el enlace `Ver Panel Vendedor` vuelve a disparar prefetch en pointer/focus como respaldo.

Esto reduce el trabajo inicial sin perjudicar la velocidad del Dashboard.

### Caché compartida

Se creó `runtimeCache.js` y `sharedResources.js`.

Política actual:

- ubicaciones: 30 s;
- productos: 60 s;
- descuentos: 60 s;
- vendedores: 60 s;
- categorías: 90 s.

La caché combina solicitudes concurrentes iguales para evitar dos lecturas simultáneas del mismo recurso. Se limpia al cerrar sesión y al perder la sesión, evitando reutilizar información entre usuarios.

No sustituye Firestore como fuente de verdad y utiliza TTL corto para datos mutables.

### Firestore

Las consultas de ventas continúan acotadas por:

- permisos;
- rango temporal;
- ubicación cuando corresponde;
- inicio inclusivo;
- final exclusivo.

`listSalesByRange` conserva su caché temporal y deduplicación. Métricas ejecuta una consulta de ventas para el rango/ubicaciones y calcula el resto de las dimensiones sobre el mismo conjunto en memoria, en vez de ejecutar una query independiente por tarjeta o gráfico.

### Listeners

Se mantiene realtime únicamente donde aporta valor operativo: stock de la ubicación activa del vendedor.

`useSellerLocationStock` conserva un único `onSnapshot` para la ubicación activa y ejecuta `unsubscribe` al cambiar ubicación o desmontar el Panel Vendedor.

La botonera mantiene un único `keydown` por contexto operativo y lo elimina al desmontar o deshabilitarse.

## Botonera Bluetooth

Antes cada tecla realizaba búsquedas lineales sobre acciones, descuentos y productos.

Ahora se construyen mapas en memoria:

- tecla/código → producto;
- tecla/código → descuento;
- tecla/código → acción.

La resolución de cada pulsación pasa a acceso de mapa O(1), manteniendo compatibilidad con `key`, `code` y `location` física del teclado.

## Dashboard

### Cargar Stock

Se agregó junto a `Venta Rápida`.

Flujo:

`Dashboard → Cargar Stock → elegir ubicación activa → /gestion/locations/{id}/stock`

El selector usa la lista de ubicaciones que Dashboard ya cargó. No realiza una segunda consulta idéntica sólo para abrir el acceso rápido.

### Métricas

El panel de ritmo de ventas ofrece `Ver todas las métricas` y navega mediante SPA a `/gestion/metrics/sales`.

## Módulo Métricas

### Fuente única de filtros

`SalesMetricsPage` mantiene un solo estado de filtros con:

- tipo de período;
- fecha/día;
- mes;
- año;
- desde/hasta;
- ubicaciones;
- vendedores;
- categorías;
- productos;
- descuentos;
- formas de pago.

Todos los widgets consumen el mismo `filteredSales` y la misma llamada a `calculateMetrics`.

### Período

Soporta:

- Día.
- Mes.
- Año.
- Rango personalizado.

Los límites se calculan con `America/Argentina/Buenos_Aires`, inicio inclusivo y final exclusivo.

### Ubicaciones

- Todas las ubicaciones.
- Activa.
- Inactiva.
- selección múltiple.

La actividad se determina mediante `locationActivity`, la misma lógica del módulo Ubicaciones. Las bajas lógicas no se incluyen.

### Vendedores

Se permite Todos/uno/varios. Las opciones se derivan de las ventas disponibles dentro del rango autorizado, evitando una consulta administrativa adicional a `users` sólo para construir el filtro.

### Productos

Las categorías y productos proceden de Firestore. No existen categorías comerciales hardcodeadas en el filtro.

Permite:

- todos;
- categoría completa;
- productos individuales;
- múltiples selecciones.

### Descuentos

Permite:

- Todos los descuentos.
- Sin descuento.
- descuentos configurados reales.
- selección múltiple.

Cuando una venta histórica no posee detalle suficiente no se inventa información.

### Formas de pago

- Efectivo.
- Débito.
- Crédito.
- Alias / transferencia.
- selección múltiple.

### Resumen

Calculado desde el mismo dataset:

- Total vendido.
- Cantidad de ventas.
- Unidades vendidas.
- Ticket promedio.
- Total de descuentos.

### Evolución

Gráfico SVG ligero sin incorporar una librería pesada de charts.

Granularidad:

- Día → hora.
- Mes → día.
- Año → mes.
- Rango corto → día.
- Rango medio → semana.
- Rango largo → mes.

### Productos y ranking

La agregación de productos se calcula una sola vez. El Ranking reutiliza esa misma lista ordenada y no vuelve a recorrer las ventas.

### Formas de pago y +2 pagos

El donut se calcula por monto cobrado.

Para una venta de $100.000:

- efectivo $40.000;
- débito $60.000;

las métricas agregan exactamente $40.000 a efectivo y $60.000 a débito. No contabilizan $100.000 en ambos medios.

### Ubicaciones

Muestra monto, ventas y unidades y permite ordenar por esas tres dimensiones.

### Vendedores

Muestra total, cantidad de ventas, unidades y ticket promedio.

### Descuentos aplicados

Muestra, cuando el documento histórico contiene la información:

- nombre;
- guardado/manual;
- cantidad de usos;
- monto vendido asociado;
- importe descontado;
- porcentaje sobre las ventas filtradas.

## Conectividad

Se creó una fuente compartida de estado:

- `online`;
- `offline`;
- `reconnecting`.

Existe un solo par de listeners de navegador para `online/offline`.

El indicador de administración es interactivo y abre `Estado de conexión`.

`Reconectar`:

1. revisa `navigator.onLine`;
2. realiza `getDocFromServer` únicamente sobre el perfil actual;
3. no descarga colecciones;
4. actualiza el estado compartido.

### Decisión final sobre offline

Por indicación posterior del usuario, **NO se implementó modo solo lectura**.

Se conservan:

- `saveSellerPendingSale`;
- cola IndexedDB;
- reserva local de stock pendiente;
- `syncPendingSales` / sincronización equivalente;
- ID remoto determinístico;
- idempotencia;
- revalidación real de stock al recuperar conexión;
- errores visibles sin confirmar operaciones fallidas.

Una venta pendiente sigue informándose como pendiente y no como venta confirmada en Firestore.

## Menú mobile

Se mantiene scroll vertical nativo:

- `touch-action: pan-y`;
- `-webkit-overflow-scrolling: touch`;
- sin handlers `touchmove` por píxel;
- sin `preventDefault` sobre el scroll;
- `overscroll-behavior` acotado;
- animaciones cortas mediante `transform` y `opacity`;
- sin backdrop blur en mobile;
- cierre con Escape y restauración de foco.

## Mobile y carga visual

- productos del vendedor mantienen `loading="lazy"`;
- categorías largas utilizan `content-visibility: auto` para reducir trabajo de elementos fuera de pantalla;
- filtros Métricas pasan a paneles táctiles y una columna en teléfonos angostos;
- modales/listas poseen scroll interno y overscroll acotado;
- controles críticos mantienen áreas táctiles compatibles con ~44 px;
- no se introdujo scroll horizontal general.

## Accesibilidad

- foco visible;
- `aria-pressed` en filtros segmentados;
- checkboxes con label;
- estados de conexión con texto e icono;
- gráficos con `role="img"` y alternativa textual;
- Escape y restauración de foco en navegación mobile;
- `prefers-reduced-motion` respetado.

## Medición de bundle

### Antes de este envío

Build exitoso anterior del PR:

- `index`: 996,69 kB minificado / 261,18 kB gzip.
- `ManagementApp`: 178,38 kB / 50,91 kB gzip.
- sólo existían esos dos chunks JavaScript principales de aplicación.

### Después

Build del envío:

- núcleo `index`: ~158,28 kB / 50,73 kB gzip;
- `ManagementApp`: ~44,91 kB / 15,16 kB gzip;
- `SellerPanel`: ~40,85 kB / 12,43 kB gzip;
- `SalesMetricsPage`: ~20,89 kB / 7,33 kB gzip;
- `LocationsPage`: ~17,95 kB / 6,58 kB gzip;
- `LocationDetailPage`: ~38,64 kB / 11,04 kB gzip;
- `Storefront`: ~67,20 kB / 19,00 kB gzip;
- otros módulos pequeños poseen chunks independientes.

Firebase/autenticación continúa formando un chunk grande que se necesita para login y Firestore. No se eliminó funcionalidad ni se sustituyó Firebase para reducirlo artificialmente.

La mejora relevante es que vendedor, métricas, ubicaciones, tienda y módulos secundarios ya no se ejecutan todos durante el primer render del Panel General.

## Riesgos y pendientes

1. Sin credenciales de un usuario real no puede automatizarse desde CI una medición exacta click → primer producto visible en un dispositivo físico; la reducción de bundle, consultas y búsquedas sí queda medida/estructuralmente validada.
2. La suite no sustituye una prueba táctil real en Safari iPhone y Chrome Android. El CSS evita interceptores de touch y aplica reglas compatibles, pero conviene validar el dispositivo operativo real.
3. `QuickSalesPage` conserva `createQuickSale` por sus campos específicos de canal/DNI/entrega. No se creó una tercera lógica.
4. Las reglas Firestore modificadas en envíos anteriores se validan con emulador. Netlify despliega frontend pero no publica reglas Firestore por sí mismo.
