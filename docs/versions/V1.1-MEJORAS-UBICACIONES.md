# Versión 1.1 · Envío 2 · Mejoras del módulo Ubicaciones

## Documento de origen

Este envío implementa el documento funcional entregado para mejorar el módulo **Ubicaciones**, sin reconstruir la aplicación ni modificar los demás módulos.

## Resumen de la inspección

La aplicación ya contaba con una base correcta y reutilizable:

- `LocationsPage.jsx`: listado, filtros, creación, edición y ciclo de vida de ubicaciones.
- `LocationDetailPage.jsx`: estructura interna con Productos, Cargar stock, Vendedores y Descuentos.
- `locationManagementService.js`: catálogo maestro, configuración local, cargas transaccionales de stock, asignación sincronizada de vendedores, descuentos y auditoría.
- `dashboard.js`: unión dinámica entre producto maestro y stock local, más validación de descuentos.
- `permissions.js`: permisos por rol, permisos explícitos y denegaciones individuales.
- `firestore.rules`: seguridad por usuario activo, rol, ubicación permitida y tipo de operación.
- `FM-stock-y-ventas`: formulario de producto con nombre, abreviación, categoría, descripción, precio entero, imagen local, botonera y estado.

La decisión fue extender estas piezas y no crear catálogos, ubicaciones, usuarios, descuentos ni movimientos paralelos.

## Cambios funcionales implementados

### Ubicaciones fijadas

- El administrador puede fijar o desfijar ubicaciones desde cada tarjeta.
- Se permiten hasta cuatro ubicaciones fijadas.
- La quinta ubicación se rechaza con un mensaje que indica que primero debe desfijarse otra.
- La preferencia se guarda en `users/{uid}.pinnedLocationIds`.
- Las referencias a ubicaciones eliminadas o no visibles se limpian de forma segura.
- El orden utilizado es el orden de fijación.
- Después de las fijadas se ordenan activas, próximas, pausadas, inactivas y finalizadas.

### Acceso rápido a Cargar stock

- Cada tarjeta incluye la acción **Cargar stock**.
- La ruta abre directamente `/gestion/locations/{locationId}/stock`.
- Si la ubicación no está activa, la acción queda deshabilitada y explica el motivo.
- La sección interna también vuelve a leer la ubicación antes de ejecutar la carga.

### Estructura interna

Se conservaron únicamente las cuatro secciones operativas existentes:

1. Productos.
2. Cargar stock.
3. Vendedores.
4. Descuentos.

Las rutas directas son:

- `/products`
- `/stock`
- `/sellers`
- `/discounts`

En mobile se conserva el selector compacto existente.

### Productos desde una ubicación

- Se agregó **Agregar nuevo producto**.
- El formulario reutiliza el enfoque funcional de `FM-stock-y-ventas`.
- Campos incluidos: nombre, abreviación, categoría, descripción, precio predeterminado entero, alertas amarilla y roja, estado, imagen local y tecla de botonera.
- Se controla que la abreviación tenga como máximo ocho caracteres.
- Se evita crear otro producto con el mismo nombre o abreviación.
- Se mantiene una única definición en `products/{productId}`.

### Alcance local o global

- La opción predeterminada es **Solo esta ubicación**.
- La opción **Todas las ubicaciones activas** requiere permiso administrativo.
- La asignación global requiere confirmación explícita.
- Cada configuración local se guarda en `locationStock/{locationId}/items/{productId}`.
- Todos los stocks nuevos comienzan en cero.
- No se asigna el producto a ubicaciones eliminadas o finalizadas.
- La operación usa un batch y deja auditoría.

### Productos agrupados por categoría

- Los productos se presentan en paneles expandibles por categoría.
- Cada grupo indica nombre y cantidad de productos.
- Se mantienen búsqueda, filtro de categoría y filtro de estado.
- Cada producto conserva precio, alertas, disponibilidad, stock y configuración local.
- La representación mobile utiliza tarjetas apiladas y no tablas anchas.

### Cargar stock y contraste

- La regla de ubicación activa se conserva en interfaz y servicio.
- Se muestra stock actual, cantidad ingresada y stock final.
- Los textos numéricos usan tonos oscuros `#2F2924` y `#76510F`.
- Los campos enfocados usan borde dorado oscuro y anillo visible.
- Los controles deshabilitados tienen texto legible.
- Las reducciones continúan requiriendo confirmación.
- Cada operación sigue generando movimientos y auditoría mediante la transacción existente.

### Catálogo local de imágenes

- Se creó `src/data/productImages.js`.
- El catálogo utiliza las imágenes existentes en `public/images/flor-mia/products/`.
- Incluye un placeholder local de imagen pendiente.
- El formulario permite buscar, filtrar, seleccionar y previsualizar imágenes.
- Firestore guarda solamente `imageUrl`, `thumbUrl`, texto alternativo, estado y nombre del archivo.
- Se rechazan rutas `data:` y `blob:`.
- No se utiliza Firebase Storage ni se guardan archivos binarios o Base64.

### Vendedores

- La lista principal contiene únicamente vendedores asignados.
- Cada vendedor muestra fotografía cuando existe o iniciales como respaldo.
- Se muestran nombre, email y estado.
- Los vendedores no asignados aparecen únicamente dentro del modal **Asignar vendedor**.
- El modal permite buscar y seleccionar varios usuarios existentes.
- La asignación reutiliza `saveLocationSellers`, que actualiza ubicación y usuarios en una transacción.
- Se reutiliza el flujo existente de Administración para crear una cuenta nueva.
- Las altas y bajas quedan auditadas por el servicio existente.

### Descuentos

- Se continúa utilizando la colección maestra `discounts`.
- La ubicación guarda únicamente `enabledDiscountIds`.
- Se muestran nombre, tipo, valor, vigencia, restricciones y estado local.
- Los descuentos inactivos, vencidos o todavía no vigentes no pueden habilitarse.
- La validación se repite en el servicio antes de guardar.
- La operación utiliza la auditoría existente.

## Modelo de datos

### Producto maestro

`products/{productId}` contiene identidad, categoría, descripción, precio predeterminado, imagen local, botonera y estado.

### Producto por ubicación

`locationStock/{locationId}/items/{productId}` contiene disponibilidad, precio local, stock inicial, stock actual, alertas y estado local.

### Preferencias del usuario

`users/{uid}.pinnedLocationIds` contiene hasta cuatro IDs visibles para ese usuario.

### Vendedores

La relación continúa sincronizada entre:

- `locations/{locationId}.assignedSellerIds`
- `users/{uid}.allowedLocationIds`

### Descuentos

- Definición: `discounts/{discountId}`.
- Asignación: `locations/{locationId}.enabledDiscountIds`.

## Reglas de Firestore

No se amplió el acceso de Firestore para roles no administrativos en este envío.

Las funciones nuevas sensibles —fijar preferencias, crear productos maestros, asignar el producto a todas las ubicaciones y editar datos maestros— están visibles únicamente para `admin` y `general_admin`, roles que las reglas actuales ya autorizan.

Los demás perfiles conservan exactamente los permisos anteriores. Las reglas existentes siguen validando:

- usuario activo;
- ubicación permitida;
- stock no negativo;
- cargas y ajustes autorizados;
- asignación de vendedores solamente administrativa;
- descuentos solamente autorizados;
- auditoría inmutable.

Antes de habilitar creación local de productos o preferencias personales para roles no administrativos deberá realizarse una ampliación explícita de `firestore.rules` y sus pruebas. No se abrió ese permiso automáticamente para evitar una diferencia entre interfaz y backend.

## Responsive y accesibilidad

Los estilos incluyen adaptaciones para 1024, 768 y 390 píxeles, que cubren el comportamiento de 1440, 1200, 1024, 768, 480, 390 y 320 mediante diseño fluido.

Se incorporaron:

- controles táctiles de al menos 44 px;
- foco visible;
- labels y `aria-label` en acciones de icono;
- switches etiquetados;
- modales reutilizados con focus trap y restauración del foco;
- estados con texto además de color;
- avatares con iniciales accesibles;
- `prefers-reduced-motion`;
- tarjetas apiladas sin tablas anchas en mobile.

La validación automática confirma estructura y build. La comprobación visual final en dispositivos físicos debe realizarse desde el Deploy Preview.

## Cómo agregar futuras imágenes

1. Copiar el archivo optimizado a `public/images/flor-mia/products/`.
2. Preferir WebP o AVIF, una proporción consistente y menos de 500 KB cuando sea posible.
3. Agregar una entrada de producto que utilice esa ruta o incorporar la entrada explícita al catálogo de `src/data/productImages.js`.
4. Hacer commit en la rama de versión.
5. Netlify publicará la imagen y aparecerá en el selector.
6. Firestore conservará únicamente la ruta elegida.

## Riesgos y tareas pendientes

- El Deploy Preview utiliza actualmente el mismo proyecto Firebase configurado para la aplicación; las pruebas que creen productos, asignen vendedores o modifiquen stock afectan esos datos.
- La inspección visual en dispositivos físicos queda a cargo del usuario mediante el Deploy Preview.
- La asignación global está optimizada para la cantidad actual de ubicaciones. El servicio limita la operación para no superar el batch de Firestore.
- La creación de producto y preferencias para roles no administrativos permanece deshabilitada hasta ampliar y desplegar reglas específicas.
- Las imágenes futuras requieren commit porque no se implementó carga desde navegador ni Firebase Storage.

## Despliegue

El Pull Request borrador actualiza automáticamente el mismo Deploy Preview de Netlify. No debe fusionarse con `main` hasta completar la prueba funcional y visual.
